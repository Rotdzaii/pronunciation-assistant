## 3. Relationship Proposal

`vocabulary_items` stores word metadata used for pronunciation practice. It should describe the target word, phonetic display, Vietnamese meaning, sample sentence, pronunciation focus phonemes, common learner mistake tags, topic, level, and difficulty.

`vocabulary_sets` groups `vocabulary_items` into teacher-created or system-defined practice collections. Sets can represent topics, lessons, phoneme drills, or common-mistake review groups.

`vocabulary_set_items` is the many-to-many relationship between `vocabulary_sets` and `vocabulary_items`. It should preserve set ordering and optional per-set pronunciation focus overrides without duplicating item metadata.

`vocabulary_assignments` assigns a vocabulary set to a student or class. Because no class table was found in the repository, `class_id` should not be added until the class model is confirmed. A safe first assignment model should support direct student assignment only, or wait entirely until teacher/class relationships are designed.

`vocabulary_practice_history` links a vocabulary item attempt to existing `practice_history`. It should store the vocabulary context around the attempt:

- which vocabulary item was practiced
- which set the item came from, if any
- which assignment caused the attempt, if any
- which `practice_history` row contains the actual pronunciation attempt

Important: `practice_history` remains the source of truth for pronunciation attempts. The vocabulary feature should add context around `practice_history`, not create a competing attempt record.

Recommended foreign-key direction, pending confirmation:

- `vocabulary_set_items.vocabulary_set_id` -> `vocabulary_sets.id`
- `vocabulary_set_items.vocabulary_item_id` -> `vocabulary_items.id`
- `vocabulary_practice_history.vocabulary_item_id` -> `vocabulary_items.id`
- `vocabulary_practice_history.vocabulary_set_id` -> `vocabulary_sets.id`
- `vocabulary_practice_history.vocabulary_assignment_id` -> `vocabulary_assignments.id`
- `vocabulary_practice_history.practice_history_id` -> `practice_history.id`
- User ownership columns such as `created_by`, `teacher_id`, and `student_id` should reference the same user identity target already used by `profiles` and `practice_history`.

Safe delete behavior:

- Deleting a vocabulary item should not delete `practice_history`.
- Deleting a vocabulary item should probably be restricted or soft-deleted with `is_active = false`.
- `vocabulary_practice_history.practice_history_id` should not cascade-delete the `practice_history` source of truth.
- Set membership rows can cascade when a set is deleted, but sets themselves should likely be soft-deleted after real practice data exists.

## 6. Migration Risk Notes

- Wrong foreign key target: referencing `profiles(id)` when existing data uses `auth.users(id)`, or the reverse, can break inserts and joins.
- Unsafe RLS policy: allowing teacher access without a confirmed teacher-student or class relationship could expose all student practice data.
- Duplicate source of truth: storing score, status, problem phonemes, and feedback in both `practice_history` and `vocabulary_practice_history` can create inconsistent results.
- Accidental history deletion: cascading deletes from `vocabulary_items` into `vocabulary_practice_history` and then into `practice_history` would be unsafe.
- Premature `class_id`: adding `class_id` before a class table exists creates an unclear nullable relationship and may force later rework.
- Unconfirmed role helpers: writing RLS policies that depend on missing SQL helper functions will fail migration or silently diverge from backend role logic.
- Missing `updated_at` trigger: assuming automatic timestamp maintenance when the database does not provide it can create stale audit fields.
- Seed ownership ambiguity: requiring `created_by` for system seed vocabulary may make seed loading harder unless a system owner model is defined.

## 7. Recommended Safe Migration Plan

### Phase DB1

- Create `vocabulary_items`.
- Create `vocabulary_sets`.
- Create `vocabulary_set_items`.
- Do not create assignments yet.
- Do not add `class_id` yet.
- Keep seed vocabulary system-owned, likely with `created_by null`, unless a system user is confirmed.
- Use `is_active` for safe deactivation instead of hard deletes.

### Phase DB2

- Create `vocabulary_practice_history`.
- Link `vocabulary_practice_history.practice_history_id` to `practice_history.id` after confirming the existing `practice_history` primary key and delete behavior.
- Link `student_id` to the same identity target used by `practice_history.student_id`.
- Keep pronunciation attempt result fields in `practice_history`; avoid duplicating result state.

### Phase DB3

- Add `vocabulary_assignments` after confirming the teacher/class model.
- Start with student assignments if no class table exists.
- Add `class_id` only after a class table and enrollment/teacher ownership model are confirmed.
- Add RLS policies only after the project's existing RLS style and role helper approach are confirmed.

## 8. Recommendation

Do not create the migration yet.

The repository does not contain the original `CREATE TABLE` definitions for `profiles` or `practice_history`, does not show the foreign-key target for `practice_history.student_id`, and does not include current RLS policy style for the active practice tables. Creating SQL now would risk choosing the wrong identity relationship, duplicating pronunciation attempt state, or adding unsafe teacher/class access rules.

Recommended next step: create the Phase DB1 migration only after confirming the deployed Supabase schema for `profiles`, `practice_history`, role/RLS conventions, and whether any class model already exists outside this repository.
